# Development

How to set the project up, where things are, and how to run every test. For how the configurator's code is organised, see [architecture.md](architecture.md).

## What you need

| For | Install |
| --- | --- |
| The configurator, the validator and the script tests | [Node.js](https://nodejs.org/) 24 |
| The AutoHotkey version | [AutoHotkey v2](https://www.autohotkey.com/download/) on Windows |
| The PowerShell version and its tests | Windows PowerShell 5.1 (in Windows) and [Pester](https://pester.dev/) 6.2.0 or newer, the version CI runs and the only one the suite is run on (`run.ps1` stops with exit code 1 before any test when an older one, or none, is installed) |
| The end-to-end test | Windows PowerShell 5.1, Pester 6.2.0 or newer, [AutoHotkey v2](https://www.autohotkey.com/download/) and [Python](https://www.python.org/downloads/) on `PATH`, on a Windows desktop you can give up for a few minutes |
| The browser tests | Chromium for Playwright: `npx playwright install chromium` in `configurator/` |
| The Docker images | Docker with buildx |

The macropad itself only runs on Windows. The configurator, the validator and their tests also run on Linux and macOS, except the desktop-app tests, which need the Electron binary and, on Linux, a display (requiring the `electron` module downloads the binary the first time, as `npm ci` does not; they skip themselves when it cannot be had, and on Linux without a display), and the tests that need Windows, which skip themselves elsewhere: the pictures of the pad and the header tests among the browser tests ([below](#the-pictures-of-the-pad)), and a few unit tests in `configurator/electron` that need Windows paths, the real process list or the real PowerShell (in `ipc.test.ts`, `macropad.test.ts` and `syntax.test.ts`).

## Repository layout

- `config.json`: the example layout.
- `ahk/`: the AutoHotkey version (`main.ahk`, `lib/`, `commands/`, `tests/`).
- `powershell/`: the PowerShell version, its tests and its docs.
- `img/`: icon sets, one folder per icon; `icon.svg` and `logo.svg`, and the `icon.ico`, `logo.ico` and `logo.png` made from them.
- `qmk/`: the VIA/QMK layout of the EPOMAKER EK21 keypad this was built for.
- `scripts/`: the config validator, the private-details check, the version and release scripts that CI runs (`ci-version.mjs`, `ci-release.mjs`, see [releasing.md](releasing.md)) and their tests.
- `configurator/`: the web and desktop configurator (React, Vite, TypeScript, Electron).
- `Dockerfile`, `docker/`: the configurator's Docker images. See [docker.md](docker.md).
- `docs/`: these documents and their pictures.
- `Jenkinsfile`, `sonar-project.properties`, `ci/`: CI and the Jenkins job definition.
- `local/`: yours, ignored by git.

## Running the configurator

```
cd configurator
npm install
npm run dev          # the browser version; open the address it prints in Chrome or Edge
npm run electron     # the desktop app, built and started
npm run dist         # the Windows installer and portable exe, into configurator/release/
```

Press **Open folder** and pick this repository.

## Tests

> [!WARNING]
> **Photosensitivity warning.** Some of these suites open, move and close windows in quick succession, which makes the screen flash and flicker. If you have photosensitive epilepsy, or flashing affects you, do not watch the screen while they run: look away, switch the monitor off, or let CI run them.
>
> The ones that do it: the Pester suite (`powershell\tests\run.ps1`), which shows a tooltip and small test windows even when its Integration tests are left out (it builds the overlay and the delayed key and click forms but never shows them), and more with them; the end-to-end test (`powershell\tests\run.ps1 -EndToEnd`), which opens, moves, maximizes and closes windows, shows Task View and the screen capture, and switches the virtual desktop, at most three changes a second; and the desktop-app tests (`npm run test:electron`), which open and close the app's window. The configurator's unit tests and browser tests run without a visible window.

| Command | From | What it runs |
| --- | --- | --- |
| `node --test "scripts/*.test.mjs"` | the repository root | The tests of the validator, the private-details check, and the version and release scripts that CI runs (`ci-version.mjs`, and `ci-release.mjs` with its check of the changelog). |
| `node scripts/validate-config.mjs` | the repository root | Checks the layout both versions would load. |
| `npm test` | `configurator/` | The unit tests (Vitest, in Node and jsdom). Add `-- --coverage` for coverage. |
| `npm run test:browser` | `configurator/` | The app in headless Chromium: real mouse drags, keyboard, touch, small windows, a real folder handle, and pictures of the pad. |
| `npm run test:electron` | `configurator/` | Builds and launches the desktop app: drags a key, saves it to `local/config.json` and checks that the example is left alone; reopens the remembered folder; asks before the window closes on unsaved edits; creates a new folder and sets up a fresh copy in it, with its manifest; sets up an empty folder picked with **Open folder**; updates a folder whose manifest is of an older version (the bar, the dialog, the file and the manifest on disk); hands the AutoHotkey download link to the default browser and opens no window of its own; and checks that the page is sandboxed, with only the `omb` bridge. Skips itself without the Electron binary or a display; with `OMB_REQUIRE_ELECTRON=1`, as in CI, that is a failure instead. |
| `npm run lint` and `npm run build` | `configurator/` | ESLint, then the type check and the production build. |
| `powershell -NoProfile -File powershell\tests\run.ps1` | the repository root, on Windows | The Pester suite: the PowerShell version's tests (every key name its commands press exists, among them), the checks of the AutoHotkey version (it loads without an error or a warning, and its JSON parser reads what it should) and of both together (they press the same keys for each command, and build the same layout), then your own tests in `local\powershell\tests`. Its Integration tests, which need a desktop (real keys and windows, the AutoHotkey JSON parser and the same-layout check among them), are in it; `-ExcludeTag Integration` leaves them out, and so does `-Ci` (the CI run, which writes JUnit XML and measures coverage). |
| `powershell -NoProfile -File powershell\tests\run.ps1 -Integration` | the repository root, on Windows | Only the Integration tests. Add `-Ci` for JUnit XML, as CI does. |
| `powershell -NoProfile -File powershell\tests\run.ps1 -EndToEnd` | the repository root, on Windows with AutoHotkey v2 and Python | The end-to-end test of both versions, below. `-Case 'Name\|Other'` runs only the cases whose name matches; `-Repeat 12` makes each of the two Calculator series 12 times (2 by default); `-LimitMinutes 40` gives the run 40 minutes before it stops and cleans up (20 by default). |

Some tests read your `local/`, so that what you added is checked too: `run.ps1` runs your tests in `local\powershell\tests`; `Config.Tests.ps1` checks your `local\config.json` as well as the example, with your commands in `local\powershell\commands` loaded; and the AutoHotkey load test loads `ahk\main.ahk`, which includes your `local\ahk\commands.ahk`. The end-to-end test never loads anything from `local/`: it runs from a copy without it. The configurator's tests and the script tests do not read it.

### The end-to-end test

`powershell\tests\EndToEnd.Tests.ps1` starts the real macropad, the AutoHotkey version and then the PowerShell one, from a copy of `ahk`, `powershell` and `img` in a temporary folder (so your own commands in `local/` are not loaded), with a test layout, presses the macro keys with `SendInput` as a keyboard would, and checks what happened: a program window that opened and is active, a file that a fixture script wrote, a window that moved, or the exact keys that a stand-in window received (or the program's own command posted to it, such as Chrome's command for a new tab in a group). Every command of `ahk/commands` and `powershell/commands` is covered (its case runs wherever the test runs), conditional (its case needs something a PC may lack, such as a second monitor, and says what) or excluded with the reason (the power commands lock or shut down the PC); the table is `powershell/tests/helpers/EndToEndCases.ps1`, the fixtures are in `ahk/tests/e2e`. No real Chrome, PuTTY, VS Code or Visual Studio is used: small stand-in windows run under Chrome's and PuTTY's names, and the keys of the VS Code and Visual Studio commands go into a stand-in in front, which records them.

The test layout takes the display options of the example layout, `config.json` (`showFn`, `showMacroMarkers`, `showLabels`, `useMacroIcons`, `iconAction`), so the overlay under test is drawn as yours is, labels, macro markers and the Fn key among it; a test layout whose keys fill one layer gets a second, empty one. Two cases use the pointer on the overlay, in both versions, while Fn is held: `E2eOverlayLabel` reads that a key's label shows the name of its command, rests the pointer on it until the macropad shows a tooltip, then clicks it, which must run the key's command; `E2eOverlayIcon` clicks the icon of key 1, which must select layer 1 (the label of key 1 then shows the name of layer 1's first command, and key 1 runs it). The window in front must keep the keyboard through both, and a tooltip of the macropad's must be gone within 2.5 s of the overlay being seen hidden, in both versions: the tooltip goes with the overlay. The PowerShell macropad switches its tooltip off and on again where it hides the overlay (`Hide-Overlay`), so that its tip is meant to go with the hide, which these cases check; the AutoHotkey one goes when Windows sends the overlay's window `WM_MOUSELEAVE` (`OnMouseEvent` in `ahk/lib/io.ahk`; it comes when the pointer leaves the window), which is Windows' time, not measured, and the limit leaves more than twice what the case times of one build suggest it needs (up to about a second), while the PowerShell tip that ran out its own 5 s would fail it. Each finds the key on the screen from the layout's model and the overlay's controls, at the scale the overlay is drawn at, and puts the pointer back where it was.

The test also covers the `hotkeys` and `hotstrings` of a layout file, in both versions, in a layout of their own: it comes after all the others and is the only one that has them, so the key hook they bring (the PowerShell version installs its hook only for a layout that has some) cannot touch any other case. Its hotkeys are Ctrl+Alt+F9 with no window condition, Ctrl+Alt+F10 with `ifWinActive` and Ctrl+Alt+F11 with `ifWinNotActive`, both naming the program of a stand-in; their action, `E2eHotkey`, writes the name it is handed (the hotkey or hotstring as the layout writes it) to the run's `hotkeys.log`. A hotkey must run with its key kept from the window in front; pressed while its condition does not hold, it must run nothing, and the window in front must receive the key with Ctrl and Alt held. The hotstrings are typed a key at a time into a stand-in and ended with Space: `::e2ebtw` must leave exactly `by the way ` in it, and `:X:e2erun` must run its action and leave no `e2erun`. One more case presses a command's keys in that layout, which must reach the window unchanged.

`run.ps1 -EndToEnd` always starts a PowerShell process for the test, whatever shell you call it from, and the test refuses to run in any other process: its banner watches that process and cleans up when it has ended, so the process must end when the run does. Anywhere else the desktop cases skip themselves and name the command; under `-Ci` they fail instead, so that a build cannot pass with no case run.

While it runs, for a few minutes, the test has the keyboard, the mouse and the screen. It:

- shows a banner at the top of the screen for the whole run, three seconds before the first key;
- stops any macropad that runs, of either language, and starts each again at the end from its own command line and folder, also when a case fails (when the test process dies, the banner runs the clean-up below and stays up while it works), never twice: a macropad of the same script that already runs is not started again;
- opens and closes small dark stand-in windows, File Explorer, PowerShell and Command Prompt, Settings, Notepad, Control Panel and message boxes; opens and closes Calculator a few times per macropad (two series, one of second presses while it starts and one of closing and opening it again, each made twice by default; `-Repeat N` makes that N times, and a second press that came too late is made again, so `-Repeat 12` opens it 26 to 50 times per macropad); snaps, maximizes and minimizes a stand-in; shows Task View and the screen capture once per macropad, and the desktop with two presses per macropad; makes a virtual desktop, switches to and fro, and closes it, once per macropad;
- moves the mouse pointer for the delayed-click form and for the two cases that click the overlay, and puts it back.

A case does not run, saying why, where it would act on a window of yours: for example while your own File Explorer, Notepad or Settings window is open. Close those windows first for a full run. Under `-Ci` such a window fails the case instead, since the CI desktop must be clean. Only windows the command itself could pick count (visible ones, as its helper looks for them), so a hidden console is not one. A key is pressed only into the window the case names, never into whatever is in front: on your desktop, if another window has the keyboard, the case fails and says which, and nothing takes the keyboard back from you (while a window of the test's own still has the keyboard, the press waits up to 3 s for the named window and says so in the log: Windows hands the keyboard over a moment after a window is minimized or closed); only under `-Ci` is a window of Windows' own shell that came up by itself (Snap Assist, the desktop) put away once. The exceptions are keys that no window gets: Fn, the layer keys and the exit key, which the macropad's own hook takes, and the shell's own chords, Win+Ctrl+Left, Right and F4 to reach and close a virtual desktop the test made and Win+D to bring back the windows after Show Desktop. A conditional case does not run where what it needs is missing (Task Manager and Services need a standard user: for an administrator they would ask for or take elevation; Task View needs an English display language, since only its translated title tells it from Snap Assist and Alt+Tab; Settings and Calculator need none, since their windows are found by application id; `OpenPowershell` needs a desktop with no PowerShell window that is not the test's, since the key would bring that one forward, and on the Jenkins agent the agent's own console is such a window; the second press while Calculator starts needs a machine on which Calculator's first window is still kept off the screen when the press comes, which the case measures as it runs). The run ends by listing every case that did not run, with the reason. It also lists every wait that was met only after two thirds of its limit, with the case and the place that asked for it: on a slower machine that wait is the next to fail.

A window is the test's when a case saw its own key bring it and recorded it then, and the test closes those. A window that came up after a key but that the test cannot tie to it (one that never came forward, or a second Calculator) is left open on your desktop, and the run says so; under `-Ci`, where nobody else is at the desktop, it is closed.

When cases fail with "The stand-in '...' could not be made the active window; in front is ..." (or, as a macropad starts, "the stand-in B could not be made the active window for the readiness taps; ... was in front"), a window that is not the test's keeps the front, and on the CI agent that is most often a dialog that something else left on its shared desktop. Look at the agent's desktop, and close what is in front, before you look at the code: from 2026-11-21 to 2026-11-25 a Windows Security question that another project's tests raised there failed the end-to-end stage of every branch until the machine was restarted.

A case that fails also says what the keyboard and the desktop were, read in the moment it failed, before its clean-up lets go of any key or closes anything (`Get-E2eFailureState` in `EndToEnd.ps1`). Under the failure's own message and what the command log says, a block starts with "The state at the failure, read before the clean-up let go of any key:" and gives, one line each: the keys Windows has down (`GetAsyncKeyState`) of Alt, Ctrl, Shift and Win on each side, Tab, the case's own macro key and Fn, or `none`; the window in front when the key went down and now; the key watch's record; where the pointer is and which window is under it; and the visible top-level windows, top first. A last line, `after the clean-up:`, says what was in front and down once the clean-up had run. The record is one line of every injected key since the case began (the test's own keys untagged, as a keyboard's; the PowerShell macropad's tagged `MPAD`; the AutoHotkey macropad's with its own tag), in the order the key watch got them, each in ms after the case's key went down (`-` before it, `+` after; with no key pressed, after the record began), for example `-499.8 down LAlt MPAD, -499.1 up LAlt MPAD, ..., +0.4 down F21 untagged, +41.0 up F21 untagged, +212.4 down LAlt MPAD, ...`. An `MPAD` Alt tap before the press is the harness making a window active (`Native.ActivateWindow` taps Alt when the window did not come to the front at once), not the macropad. In the `NextWindow` cases, and only there, the key watch also records each window that came in front (a WinEvent hook on its own thread, on the same clock), such as `+231.0 front 'Task Switching' (explorer.exe, XamlExplorerHostIslandWindow)`; that time is when the key watch was told, later than the change, so it is an upper bound: a window listed after a key may have come in front before it. Elsewhere the record has only the window in front when it began. Nothing of this attaches to another thread's input: an attach would reset the key state that thread reads. The `NextWindow` case also prints one line in each macropad, passed or failed: `End-to-end NextWindow timing, <ahk|ps>, the case 'NextWindow' (passed): Alt down +8.6, Tab down +11.1, Tab up +17, Alt up +22.7 ms after the key went down (the key went up not seen); Alt down to Tab down 2.5, Tab held 5.9, Tab up to Alt up 5.7, Alt held 14.1 ms`, the command's own four keys as the key watch saw them (the AutoHotkey macropad's hook takes the macro key, so its key-up is not seen there). Nothing fails on these times. `E2eOverlayIcon` and `E2eOverlayLabel` print one more in each macropad, before their result line, passed or failed: `Overlay tooltip, <ahk|ps> <case>: showing when the overlay hid, gone after <n> ms (limit 2500 ms)`, or `none was showing when the overlay hid`, or `still showing at the limit`; it is how long that tooltip took to go, counted from just before the wait that fails the case at the limit, so up to one look (tens of ms) more than the wait's own count: a figure a little over the limit can be a pass.

Why it is there: in the first build of 1.0.7 (`feat/1.0.7` #1) the PowerShell `NextWindow` case failed once of 245 cases: Windows' task switcher ("Task Switching", `XamlExplorerHostIslandWindow`) stayed in front for more than four seconds after Alt+Tab, although the macropad ran the command once, start to done; the AutoHotkey `NextWindow` passed, and no script had changed since the last green release build. The clean-up had let go of any key before anything was read, so what was held could not be told. A probe branch then pressed `NextWindow` 34 times in each macropad on the CI agent (the case itself, 25 presses into a running macropad, and 8 presses each into one started again for it), and no press left the switcher in front, in either version. It measured the one difference in how the two send the chord: the AutoHotkey version sends its four key events in one `SendInput` call and held Alt 6 to 59 ms over the 25 presses (median about 16), while the PowerShell version sent them in four calls with its own work between them and held Alt 43 to 216 ms (median about 147: 7 to 24 ms from Alt down to Tab down, Tab held 17 to 157 ms, 14 to 157 ms from Tab up to Alt up). On a freshly started PowerShell macropad the first use cost 220 to 316 ms before Alt went down, not between the keys. Since then the PowerShell version sends a chord's events in one call too, as a correction of how it sends keys; the cause of the failure was not found, and that change is not known to fix it. Its `NextWindow` timing line should now look like the AutoHotkey one. If the switcher stays in front again, start from the account: an `LAlt` or `LCtrl` down means a key was held (Ctrl+Alt+Tab keeps the switcher open); `none` with the command's `up LAlt MPAD` in the record, and the switcher's `front` line, mean that Windows had every key up and the switcher stayed anyway.

Both macropads tell the test when a key's command has finished. The test starts each with `OMB_E2E` and `OMB_E2E_DIR` set, and with both set the macropad appends to the run's `commands.log` a line when a command that a key or a click on the overlay runs starts, and one when it has returned or thrown: `start <command>`, `done <command>` or `failed <command>: <message>` (the message on one line), where `<command>` is the function the layout names. The AutoHotkey version writes them in `RunMacroAction` (`ahk/lib/io.ahk`), the PowerShell version in `Invoke-EngineMacro` (`powershell/lib/Engine.ps1`), which also runs the hotkeys and hotstrings of `config.json` (the AutoHotkey version's call their action themselves and write nothing). A press the macropad did not take, or dropped while another command ran, writes nothing, and a command that never returns, or that the macropad's exit ended, writes only its start. Without `OMB_E2E` nothing is written, so a macropad you start yourself never writes it. Where the test waited for a command to be done, by a fixed time or a mark the command wrote, it now waits for these lines: the taps that check that a macropad is ready go on until the log says `done E2eMark`; a case that checks keys counts them once its command's `done` is there (and still gives a key on its way 300 ms to arrive); the second press of an opener case comes once the first press's command has finished, and must finish too; `E2eStep` presses again once its first run has finished, and says what the second press's run came to; a case whose command waits for a window that never comes (Chrome with no window, the helpers' five-second wait) waits for its `done`, and Chrome's then gives keys on their way 300 ms before it checks that none came. The Calculator series presses while the first press's command still runs, on purpose; it only says how many times the command ran for how many presses. A `failed` line after a case's press, of the case's own command or of `E2eMark`, fails the case (a late one of the command an earlier case ran does not), and a case that fails after its press says what the log says of its command: never started (the macropad did not take the key), started and not finished, finished (so what is missing is what it did), or failed, with the lines since the press.

There is one clean-up, and every run ends through it. A run that reaches its end runs it on its own folder. A run that did not end itself (a crash, a Jenkins abort) is cleaned up by its banner, by the next run, or at once by `powershell -NoProfile -File powershell\tests\run.ps1 -EndToEndCleanup`. It ends the run's processes, closes the windows and virtual desktops it opened, lets go of held keys, starts again the macropads it stopped and removes its folder. It touches only what the run's state file shows is still the run's: each process by its pid and start time, each window by its handle, process and class, each virtual desktop the test made by its id. Everything a run starts works in the run's folder (the test itself, its stand-in windows, the macropads under test and through them whatever a command starts; the banner works in the temporary folder), never in the checkout the test was called from. A process that runs from the run's folder or works in it and that started after the run's test did (a program a command started and that outlived its window) is the run's too: it is ended, and the clean-up says which, with its start time, its parent, its working directory and its command line, since the folder cannot be removed while it lives. One that started before the run did (your own shell, standing in a kept folder) is left alone, and named when the folder cannot be removed. A window is closed when it is off the screen: some programs keep a closed window, hidden, for a while. What it cannot check (a process whose start time cannot be read) it leaves alone and reports. What it could not do stays in the state file, and the folder with it, for the next clean-up to try again: the folder is removed only when every step succeeded. Of a folder from before Windows last restarted, no process or window it names is touched (they ended with Windows): the macropads that run stopped are started again, the folder is removed, and a virtual desktop it names that is still there is reported, to close by hand. A state file that does not say when Windows had started is treated the same way, but reported as a problem: nothing says that what it names has ended. A lock that a crashed clean-up left is reported and cleared. One clean-up works on a run at a time; another waits for it, then looks at what is left. Whenever it changes the screen a banner is up: the run's own, which goes last, or one the clean-up shows for as long as it works. It exits 1 when anything was not done; what it cleared is done, whichever run left it. The Jenkins stage runs it before and after the test, and a clean-up that fails fails the build. Before the test it runs it with `-EarlierBuilds`: in a Jenkins build only (never on your desktop, where your shells stand in the checkout) the clean-up first ends every process that runs from the workspace or works in it and that started before the clean-up did, the build's own steps left out, and prints each one. That is what an earlier build left, or an earlier stage of this build in the same workspace (the Pester stage, on the same machine); it is cleared, not held against the end-to-end test. The stage starts even when the workspace cannot be removed because such a process still works in it: it checks out into the folder and removes what is not part of the checkout.

### Where a configurator test goes

| File name | Runs in | Use it for |
| --- | --- | --- |
| `*.test.ts`, `*.test.tsx` | Node or jsdom (`vite.config.ts`) | Logic, state, and anything that does not depend on layout. Fast, and counted in coverage. |
| `*.browser.test.tsx` | headless Chromium (`vitest.browser.config.ts`) | Anything that needs real sizes and real input: dragging, focus, scrolling, the code editor. Helpers are in `test/browser/harness.tsx`. |
| `e2e/*.e2e.test.ts` | the real desktop app (`vitest.electron.config.ts`) | What only the Electron shell does: the bridge, the sandbox, remembering the folder. |

jsdom does not lay anything out, so every element measures 0 by 0 there and a drag cannot be tested. That is what the browser tests are for.

A browser test sends its keys, clicks, pointer moves and touches through the harness in `test/browser/` (`keyboard`, `click`, `drag`, `hover` and the others in `harness.tsx`), not through Vitest's `userEvent` itself, and awaits each one: the lint (`@typescript-eslint/no-floating-promises`) fails a promise in a browser test that is not awaited. Between two tests the harness waits for the command still going and takes the app away, and it refuses a command sent after its test has ended, or one of more than 20 moves or presses, so that a test that ran past its limit cannot type into the next. The summary of `npm run test:browser` shows 5 tests as "expected fail": they are the tests in `src/ui/isolation.browser.test.tsx` that run past their limit on purpose (`it.fails`), each followed by a test that checks it left nothing behind. They prove those protections and are not defects.

### The pictures of the pad

`src/ui/visual.browser.test.tsx` compares screenshots of the grid with the references in `src/ui/__screenshots__/`. Text is drawn with the fonts of the machine, so the references are Windows ones and the suite skips itself on other systems. After a deliberate change to how the grid looks, remake them and check the new pictures before committing:

```
npx vitest run --config vitest.browser.config.ts src/ui/visual.browser.test.tsx --update
```

A change to the width of a side panel can move the pad by half a pixel at the tests' window size, which makes every picture one pixel wider. Run this suite after such a change too.

The tests that the header fits on one row (`the header, drawn with the fonts of Windows` in `src/ui/layout.browser.test.tsx`) skip themselves off Windows for the same reason: a wider font wraps the header, as it is built to do.

## Icons and logo

`img/icon.svg` is the hotdog; `img/logo.svg` is the hotdog on a key. Three files are made from them: `img/icon.ico`, the hotdog, is the tray icon of both macropad versions; `img/logo.ico`, the logo, is the icon of the desktop app (its program, its installer, its window and its taskbar button: `configurator/electron-builder.yml` and `configurator/electron/main.ts`); and `img/logo.png` is the logo at 512 px, which the web page shows beside `img/logo.svg` as its icon (`configurator/index.html`). The page and the desktop app have the same icon, and a running macropad keeps another, so the two are told apart in the taskbar and the tray. After editing an SVG:

```
cd configurator && node scripts/make-icon.mjs
```

`docs/img/icon.png` is the hotdog at 400 by 400 pixels: the picture of the hotdog Studio organisation on GitHub. Nothing in the project reads it, and `make-icon.mjs` does not remake it. It lies in `docs/img`, not `img`, so a folder the configurator sets up does not get it.

## Keeping private details out of git

`local/denylist.txt` lists strings that must never be committed, one per line. `scripts/check-private.mjs` fails when one would reach git. Run it from git hooks so nothing slips through:

```
printf '#!/bin/sh\nexec node scripts/check-private.mjs --staged\n' > .git/hooks/pre-commit
```

## CI

Jenkins runs the `Jenkinsfile`, one stage after the other:

1. Gives the build its version (`scripts/ci-version.mjs`). On `develop` it also checks that `CHANGELOG.md` has the heading of that version and nothing under **Unreleased** ([releasing.md](releasing.md#the-changelog)).
2. Validates `config.json` and runs the script tests.
3. Installs, lints and unit-tests the configurator on the Linux agent, without the Electron binary: `npm ci` does not fetch it (the `electron` package has no install script), and nothing there requires the `electron` module, which would.
4. Runs the browser tests in headless Chromium. The agent needs Chromium's system libraries (`npx playwright install-deps chromium`, once, as root); set the `OMB_SKIP_BROWSER_TESTS` global to skip the stage on an agent without them.
5. Builds the configurator.
6. On every branch: runs the Pester suite (`run.ps1 -Ci`) on the Windows agent (`windows-x64`), without its Integration tests, which `-Ci` leaves out. That run also measures how much of the PowerShell version's code (`powershell\lib`, `powershell\commands`, `powershell\config.ps1`) the suite executes: the build's console shows a line `Covered N% / 75%. ... analyzed Commands in ... Files.` (75 is Pester's default target; nothing fails on it), and the JaCoCo file `results/pester/coverage.xml` is archived with the build. When coverage was first measured, in builds #3 and #4 of the branch `feat/1.0.7` (26 November 2026), the suite measured 85.15% of 2,323 commands in 30 files (the console line read `Covered 85.15% / 75%. 2,323 analyzed Commands in 30 Files.`). Every change to the PowerShell version's code moves that figure, so the console line of a build, or its archived `coverage.xml`, gives the figure for the code that build ran; one well below 85% is worth a look. SonarQube cannot read PowerShell, so this figure is not part of its gate.
7. On every branch: runs the Integration tests (`run.ps1 -Ci -Integration`) on the Windows agent with a real desktop (`windows-desktop`).
8. On every branch: runs the end-to-end test (`run.ps1 -Ci -EndToEnd`) on that agent, with its clean-up before and after.
9. On every branch: runs the configurator's unit, browser and desktop-app tests on that agent, with the Electron binary, so the cases that skip themselves off Windows run here, and with `OMB_REQUIRE_ELECTRON=1`, so the desktop-app tests fail rather than skip when the agent has no Electron binary or display. Right after `npm ci` the stage downloads the Electron binary (`npx --no install-electron`, the package's own command; a failed download stops the stage there with `the Electron binary could not be downloaded`, and the stage then prints `the Electron binary is in place`, or stops with `the Electron binary is missing after install-electron`) and Playwright's Chromium, through the agent user's own caches.
10. Sends everything to SonarQube, with the coverage of the unit and the browser tests on Linux, and waits for the quality gate.
11. On `develop` only: packages the desktop app on the Windows agent (`windows-x64`), and builds the Linux images for both architectures, starting each one to check that it serves the page. The arm64 image is started on the arm64 agent (`linux-arm64`).
12. On `develop` only: publishes all of it as a release. [releasing.md](releasing.md) has the version scheme and the order of the steps.

So every suite runs in CI. What still does not run there is a test that skips itself for want of something the agent lacks: above all the conditional end-to-end cases, which run only on a desktop that has what they need, and a Pester test that skips itself in the same way, such as the one of the default playback device on a machine without one. In the first build of 1.0.7, on the Windows agent with a desktop, four end-to-end cases did not run, in each of the two macropads: `NextScreen` and `PreviousScreen` (the agent has no second monitor), `OpenPowershell` (the agent's own console is a PowerShell window that is not the test's) and `OpenCalculator (second press while it starts)` (the second press never came while the first Calculator window was still kept off the screen). Those are facts of that agent, not of every machine; [the end-to-end test](#the-end-to-end-test) says what each conditional case needs. The end-to-end stage's log ends with the list of cases that did not run, with the reason, and the JUnit reports of the other stages mark each skipped test.

The `Jenkinsfile` header lists the globals, such as `OMB_NTFY_URL` for build notifications.

The Jenkins job is a multibranch pipeline defined in `ci/jenkins-job.xml`. It checks out over SSH and scans for new commits every 2 minutes. To create it, or update it after editing the XML, put `JENKINS_URL` and `JENKINS_CREDENTIALS_ID` in `local/ci/jenkins.env` and run:

```
JENKINS_USER=<user> JENKINS_TOKEN=<api token> sh ci/create-jenkins-job.sh
```

The first analysis creates the SonarQube project `hotdog-Studio_open-macro-builder` if the Jenkins token may create projects. Otherwise, create it in SonarQube first.
